# V2 Manual Crypto Test Plan

> This plan requires **exact invoice amounts** as generated by the API/UI at
> test time. Do NOT use approximate values ($5, $10) or hardcoded BTC/LTC
> amounts. The V2 invoice is fixed-atomic-amount; underpayment or overpayment
> by even 1 satoshi/litoshi will leave the flow in `awaiting_payment`.

---

## Prerequisites

- A funded BTC test wallet with sufficient balance for the invoice amount + miner
  fee (invoice ~$5 USD + ~2× expected fee buffer).
- A funded LTC test wallet with sufficient balance for the invoice amount + fee.
- Access to the V2 API (either staging or production with V2_ENABLED=true).
- A Telegram account for the client bot binding step.
- A second Telegram account (or same one with a different bot) for the informer.
- Browser DevTools or `curl` to capture exact response values.
- A log viewer (`journalctl -u naroom.service -f`) running during the test.

**Operator must provide test wallets. Do not use wallets from memory or examples.**

## Part A: Client payment intent (BTC)

### A1. Create payment intent

```
POST /v2/client/payment-intents
{
  "wallet_address": "<YOUR_BTC_TEST_ADDRESS>",
  "currency": "BTC"
}
```

**Record exactly:**
```
invoice_id:
flow_id:
payment_address:
amount_atomic (satoshis):    ← THIS IS THE EXACT AMOUNT TO SEND
amount_usd_cents:
expires_at (unix):
```

> The amount in BTC to send = amount_atomic ÷ 100_000_000.
> Example: if amount_atomic = 9800, send 0.000098 BTC. Use the exact value.

### A2. Fund required

Calculate minimum wallet balance:
- Required at-payment balance: $120 USD equivalent (post-payment balance gate)
- Invoice amount: from A1
- Miner fee buffer: at least 2× current mempool fee estimate
- Total to hold in wallet before sending: invoice + fee buffer + $120 USD equivalent

### A3. Send exact payment

- Send exactly `amount_atomic` satoshis to `payment_address`.
- Record immediately:
```
txid:
sent_at (UTC):
```

### A4. Wait for detection (worker polls every 5s)

```
Monitor: journalctl -u naroom.service -f | grep "watcher\|detected\|confirmed"
```

Poll status every 10s:
```
POST /v2/client/payment-intents/restore
{ "wallet_address": "<ADDR>", "currency": "BTC" }
```

Record state transitions:
```
awaiting_payment → detected at:
detected → payment_confirmed at:
payment_confirmed → form_ready at:
```

If state does not advance within 5 minutes, check:
- Block confirmation count on mempool.space for txid
- Worker logs for error messages

**Stop test at first discrepancy. Do NOT patch DB manually.**

Record:

### B3. Verify link status

```
GET /v2/board/tbilisi

The listing must appear in the response. Record:

```

Must return listing data. Contact must NOT be in this response (encrypted, only
available to paid helpers).

## Part E: Informer subscription

### E1. Subscribe

- Informer balance gate: wallet must have ≥ $1000 USD equivalent.
- Use BTC or LTC wallet with sufficient balance.

```
POST /v2/informer/access
{
  "wallet_address": "<ADDR>",
  "currency": "BTC",
  "city": "tbilisi"
}
```

Record:
```
raw_token:
expires_at: (15 minutes from now)
```

### E2. Connect Telegram

- Open informer bot deep link: `https://t.me/<informer_botname>?start=<raw_token>`
- Bot must respond with confirmation within 5 seconds.

### E3. Verify subscription

```
POST /v2/informer/status
{ "raw_token": "<raw_token>" }
```

Expected: `{"state": "claimed"}` or `{"state": "active"}`.

### E4. Publish new listing (trigger notification)

Publish a second listing in tbilisi (from a different client wallet).
Verify within 60 seconds that the Telegram notification arrives at the informer
bot chat.

Record:
```
notification_received_at:
notification_text_matches_listing: yes / no
```

## Part F: Post-test log check

```bash
journalctl -u naroom.service -n 200 --no-pager | grep -vE "DEBUG|INFO.*200 OK" | head -50
```

Verify:
- No wallet addresses, bot tokens, chat IDs, or txids in log output.
- No panics, fatal errors, or unexpected state transitions.
- `v2: lifecycle:` entries appear regularly (normalize + review delivery).
- `v2: InformerWorker:` entries appear with `[internal]` redaction (not raw data).

---

## Stopping criteria

Stop the test immediately and do NOT patch production data if:

1. A state transition does not occur within the expected time window.
2. A response field contains unexpected data (wrong contact, wrong amount).
3. An error log reveals PII (wallet address, token, txid in plaintext).
4. The V1 `/health` endpoint stops returning plaintext `ok`.
5. Any V2 route returns 500 without a corresponding logged (redacted) error.
